# Test Cases: STORY-20261026c0268fd1f364 — Device identity lifecycle, per-user limits, and audit continuity

## TC-01: Retire and revoke preserve history (AC1)

- **Given** an active device with job, usage, telemetry, discovery, and audit rows
- **When** an admin retires it and then revokes it
- **Then** new fleet authentication is denied with `device_retired` or `device_revoked`, the state and timestamps are visible, no child rows are deleted, and both transitions have audit events

## TC-02: The per-user limit allows five and rejects the sixth (AC2)

- **Given** a controller with `maxDevicesPerUser: 5` and four active devices for one OIDC subject
- **When** the subject enrolls a fifth and then a sixth unrelated device
- **Then** the fifth succeeds, the sixth fails with `device_limit_reached`, no sixth device row exists, and one `device.limit_rejected` audit event is written

## TC-03: A valid re-enrollment replaces the predecessor (AC3)

- **Given** an active device and a new daemon enrollment carrying its previous device ID, the same OIDC subject, and the same normalized hostname
- **When** the new enrollment completes
- **Then** the old device is retired with `supersededBy`, the new device records `replacesDeviceId`, the active count is unchanged, and the event is audited as `device.re_enrolled`

## TC-04: Invalid lineage does not merge devices (AC4)

- **Given** a previous device with a different subject, a different hostname, or `revoked` state
- **When** a new enrollment presents that previous device ID
- **Then** no lineage is written, the old device is unchanged, a `device.link_rejected` audit event records the reason, and the enrollment is subject to the normal active-device limit

## TC-05: Audit history follows the replacement chain (AC5)

- **Given** a current device with two predecessors linked through `replacesDeviceId` and `supersededBy`
- **When** an admin reads the current device's audit history
- **Then** events from the current device and both predecessors are returned newest first with cursor pagination, and payloads contain no secret-bearing values

## TC-06: The admin UI exposes lifecycle and history (AC6)

- **Given** a retired device with a predecessor
- **When** an admin opens the device list and detail
- **Then** the lifecycle badge, lineage, active-device count, and audit history are visible, retire and revoke require confirmation, the hard-delete action is absent, and state changes are announced

## TC-07: Migration preserves existing data (AC7)

- **Given** a database created before this Story with devices and audit rows
- **When** the lifecycle migration runs
- **Then** every existing device is `active`, every audit row survives with its original device ID and a backfilled subject where possible, and the new indexes exist

## TC-08: Tests cover the identity path (AC8)

- **Given** the Story's automated suite on SQLite
- **When** it runs
- **Then** the limit, replacement at the limit, link rejection, audit lineage and pagination, soft retirement, authentication denial, migration, and concurrent enrollment cannot exceed the limit, without real OIDC or network access
