## Background

Phase 1 is BYOD: users install Agentdesktop themselves, and configuration is
local-authoritative. Today the daemon only receives one controller-pushed
`DaemonConfig`; there is no signed catalog of installable agents, no local
configuration API, and no periodic catalog sync. The desktop app cannot manage
agents without a server push.

This Story adds the foundation: a signed agent catalog the daemon pulls and
verifies, a local configuration authority the desktop app writes through, and
the status reporting the controller needs. Installation and uninstallation are
covered by STORY-202610260c7300b0bf28; this Story never executes a catalog
artifact.

## Requirements

### R1: Signed agent catalog contract (MUST)

The controller MUST publish a catalog with `catalog_id`, `revision`,
`created_at`, `expires_at`, and, per entry: agent id, display name, supported
platforms and architectures, one or more versions, `install_kind: user`,
artifact URL, artifact SHA-256, artifact Ed25519 signature, install and
uninstall rules, detection rules, and an optional config schema reference.

The catalog signature MUST be Ed25519 over deterministic JSON (RFC 8785 JCS) of
the payload excluding `signature`; it covers `catalog_id`, `revision`,
`created_at`, `expires_at`, and every entry. Artifact signatures are separate:
each artifact has its own SHA-256 and Ed25519 signature over the artifact bytes,
and the catalog binds both. `canonical bytes` is therefore defined as the JCS
serialization of the catalog without its `signature` member.

The daemon MUST be configured with pinned `(key_id, public_key)` pairs. A key id
absent from the pinned set MUST be rejected. Rotation MUST support an overlap
window; a revoked key MUST be rejected even if the signature is otherwise valid.

Revisions are monotonic: a lower revision MUST be ignored; the same revision
with the same hash is unchanged; the same revision with a different hash MUST be
rejected as a protocol/tamper error; a higher revision MUST be fully verified
before it replaces the cache. An expired catalog MUST NOT authorize new
install/update jobs; the cached catalog remains readable and is marked `expired`.

### R2: Catalog delivery and periodic sync (MUST)

A new authenticated `GetAgentCatalog` fleet RPC MUST return the current catalog
or an unchanged response keyed by revision/hash. The daemon MUST sync on
startup, after reconnect, every 5 minutes with ±60 s jitter, and on explicit
request. A failed sync MUST retain the cached catalog, mark it `stale`, and retry
with bounded backoff.

### R3: Local configuration authority and effective-config resolver (MUST)

The daemon MUST support two modes: `local` (default for BYOD) and `managed`
(enterprise). The mode MUST be selected in daemon configuration and reported to
the controller.

In `local` mode every entry point — startup, reconnect, periodic sync, manual
sync, and controller push — MUST compute the effective configuration through one
shared resolver. The resolver combines non-program base fields from the startup
daemon configuration with `programs` and `programSelection` from
`local-config.yaml`:

- `programs.<id>` absent: inherit the base program value, if any;
- `programs.<id>: null`: no managed configuration for that program; the
  provider removes its managed content;
- `programs.<id>: {..}`: replace that program's managed settings; the provider
  still merges with the user's own file;
- non-program fields in `local-config.yaml` are rejected in Phase 1.

`local-config.yaml` carries a revision. `PUT` MUST require `If-Match` and MUST
return 409 with the current revision on mismatch; writes are serialized and
atomic. In `local` mode a controller push MUST NOT change `programs` or
`programSelection`; `remote-config.yaml` MUST NOT be used for programs.

In `managed` mode the controller-pushed `DaemonConfig` is authoritative and local
program edits are rejected with a structured error.

### R4: Local API for the desktop app (MUST)

The daemon MUST expose `GET /v1/catalog`, `POST /v1/catalog/sync`,
`GET /v1/agents`, `GET /v1/agents/{id}/config`,
`PUT /v1/agents/{id}/config`, and `GET /v1/sync-status` on the existing local
socket/named pipe only. It MUST validate the agent id, reject bodies larger than
256 KiB or deeper than 32 levels, validate the resulting configuration through
the `LocalConfigValidator` (R6), require `If-Match` on writes, and return
structured errors without exposing file-system paths beyond the agent's own
display path.

### R5: Status reporting (MUST)

The daemon MUST report its catalog revision, last successful sync time, and
per-agent configuration/apply status to the controller through the existing
`Connect` stream. The controller MUST store that state and expose it in the
device detail API. Rendering it in the management UI is a later Story.

### R6: Safety, secret rejection, and privacy (MUST)

Catalog entries are data only: this Story MUST NOT execute, install, or uninstall
anything from a catalog. The local config API MUST apply a `LocalConfigValidator`
before persistence:

- reject keys whose normalized names match secret-bearing patterns, including
  `apikey`, `api_key`, `token`, `secret`, `password`, `authorization`, `headers`,
  `env`, `environment`, `apiKeyHelper`, `credential`, `privateKey`,
  `clientSecret`, `cookie`, and `session`;
- reject nested `env`/`headers` maps and bodies outside the size/depth limits;
- reject non-scalar/object/array values that the validator cannot safely reason
  about.

The validator gates local BYOD writes only. Controller-managed enterprise
pass-through remains available in `managed` mode and is not exposed to the local
API. Status, logs, and error messages MUST NOT echo configuration values; they
report key names, counts, and redacted paths only. The daemon MUST NOT add a
network listener, and all writes stay in user-writable locations with no
elevation.

### R7: Compatibility and capability gating (SHOULD)

An older daemon that does not understand the new messages MUST continue to work,
and an older controller MUST ignore unknown agent state. The controller SHOULD
gate catalog actions on a reported capability so unsupported devices see no
action rather than a failed one. Existing provider behavior MUST be unchanged
when no local configuration exists.

### R8: Tests (MUST)

Unit tests MUST cover valid/tampered signatures, canonical JCS bytes, unknown and
revoked key ids, same-revision/different-hash rejection, schema rejection,
offline cache behavior, effective-config resolution across all entry points,
`If-Match` conflicts, secret-key rejection, and atomic persistence. An
integration test MUST exercise a fake controller catalog and the local API round
trip. Unit tests MUST NOT require real network access.

## Technical Design

**Approach.** Add a pull path beside the existing push path. The controller is
the catalog publisher and device registry; the daemon is the catalog consumer and
configuration authority. A single `EffectiveConfig` resolver is the only path to
`Reconciler::apply_with_report`; no entry point merges or applies configuration
on its own.

**Protocol.** Extend `crates/proto/proto/fleet.proto` with `AgentCatalog`,
`CatalogEntry`, `CatalogVersion`, `GetAgentCatalogRequest/Response`,
`AgentState`, and a `GetAgentCatalog` RPC. `AgentState` carries catalog revision,
last sync time, and per-agent config/detection status. Add a `capabilities`
field to `Hello` (for example `agent_catalog_v1`, `user_install_v1`).

**Storage.** The catalog cache is a versioned directory
`state_dir/catalog/<revision>/` containing `catalog.json` and `catalog.sig`, plus
an atomically replaced `state_dir/catalog/current` pointer. A sync writes the
complete new revision to a temp sibling, fsyncs, renames the directory, then
switches the pointer; a crash leaves either the old or the new revision, never a
partial pair. `state_dir/local-config.yaml` is written atomically with mode 0600
and a revision field.

**Signature.** Reuse `aws-lc-rs` Ed25519 verification (already a workspace
dependency). The catalog signature is over RFC 8785 JCS bytes of the payload
without `signature`; each artifact carries its own SHA-256 and Ed25519 signature
over the artifact bytes. The daemon is configured with pinned
`(key_id, public_key)` pairs, supports an overlap window for rotation, and
rejects revoked key ids. The controller signs the same JCS bytes when publishing.

**Effective configuration.** `EffectiveConfig::compute(mode, base, local,
pushed)` is the only resolver. It validates `local-config.yaml` through
`LocalConfigValidator`, applies the R3 absent/null/object semantics, rejects
non-program fields, and returns the `DaemonConfig` plus a source map. `PUT`
writes compare `If-Match` revision under a single write lock; a mismatch returns
409 with the current revision. In `local` mode the resolver ignores `programs`
and `programSelection` from pushed or cached controller payloads.

**Sync.** A single timer with jitter; manual sync is an explicit local API call.
All syncs compare revision and content hash, so an unchanged catalog does not
rewrite files or notify local subscribers.

**Controller.** A new `catalog.rs` loads and validates the signed catalog file
(the path is configuration, not an admin upload in Phase 1), serves it over the
fleet RPC, and exposes the revision. A new migration adds `device_agent_state`
and catalog metadata; all queries remain parameterized and device-scoped.

**Engineering concerns.** Candidate signals were confirmed for this change:

| Concern | Decision |
|---------|----------|
| configuration | `local`/`managed` mode; one resolver; controller push cannot set programs in `local` mode. |
| write-safety | Atomic writes, 0600, `If-Match` revisions, versioned catalog directory with a current pointer. |
| module-design | New `catalog`, `local_config`, and `sync` modules; no provider changes. |
| api-integration | One new authenticated gRPC RPC; local API remains socket-only. |
| dependency-supply-chain | Reuse `aws-lc-rs`; catalog artifacts are signed and hash-pinned. |
| observability | Expose revision, last sync, stale flag, and per-agent apply status. |
| backwards-compatibility | New fields are optional; old daemons ignore them. |

### Lateral Scan Results

- **Operation:** deliver configuration to the daemon. **Existing
  implementation:** `DaemonConfigStore` in the controller pushes over
  `Connect`. **Assessment:** keep it for enterprise mode, add a pull path for
  BYOD; do not duplicate provider write logic.
- **Operation:** apply provider configuration. **Existing implementation:**
  `Reconciler::apply_with_report` and the nine `Provider` implementations.
  **Assessment:** reuse unchanged; the local store feeds the same reconciler.
- **Operation:** report device state. **Existing implementation:** `Inventory`,
  `ConfigStatus`, and `TelemetryEvent` on `Connect`. **Assessment:** extend with
  `AgentState` rather than adding a second status channel.

## Trust Boundaries

- Signed catalog file → signature, schema, and size validation → controller
  catalog store → `GetAgentCatalog` response.
- `GetAgentCatalog` response → device mTLS/OIDC authentication → daemon
  signature and hash verification → last-known-good local cache.
- Desktop app → local socket permissions → local API validation → merge into
  `DaemonConfig` → `Reconciler` → user-level agent files.
- Local configuration → 256 KiB/depth/schema checks → atomic 0600 write →
  provider apply, with structured failure reporting.
- Agent state → authenticated `Connect` stream → controller database → device
  detail API.

## Acceptance Criteria

### AC1: A valid catalog is accepted and a tampered one is rejected (R1)

- **Given** a signed catalog with a known key id and a second copy with one byte changed
- **When** the daemon verifies each copy
- **Then** the valid copy becomes the cached catalog, the tampered copy is rejected, and the previous last-known-good catalog remains active

### AC2: Periodic and manual sync respect revision and offline state (R2)

- **Given** a daemon with a cached catalog at revision 7
- **When** the timer fires, the user triggers a manual sync, or the daemon reconnects
- **Then** it sends revision 7, does not rewrite the cache when the controller reports unchanged, writes a new revision when supplied, and marks the cache `stale` after a failed sync without deleting it

### AC3: Local configuration uses the shared effective-config resolver (R3)

- **Given** a daemon in `local` mode with base configuration and
  `local-config.yaml` revision 3
- **When** the desktop app writes revision 4 with `If-Match: 3`
- **Then** the resolver produces one effective configuration, the file is written atomically at mode 0600, `Reconciler` applies it, and a stale `If-Match` returns 409 without writing

### AC4: Local authority survives every entry point (R3, R6)

- **Given** a `local`-mode daemon with `programs.claudeCode: null` and a local override for another program
- **When** the daemon starts, reconnects, runs a periodic sync, and receives a controller push
- **Then** all four entry points produce the same effective configuration, the controller push does not change `programs`/`programSelection`, and `null` removes the managed Claude Code content

### AC5: The local API rejects invalid input and stays local (R4, R6)

- **Given** requests with an unknown agent id, a 300 KiB body, 33 levels of nesting, malformed JSON, and keys named `apiKey`, `env`, `headers`, and `apiKeyHelper`
- **When** each request reaches the local API
- **Then** each is rejected with a structured 4xx error, no file is written, status/logs show only key names and never values, and the API remains bound to the local socket/named pipe with no TCP listener

### AC6: Device state is visible to the controller (R5)

- **Given** a daemon that has synced a catalog and applied local config
- **When** it reports `AgentState`
- **Then** the controller stores the catalog revision, last sync time, and per-agent status, and the device detail API returns them

### AC7: Older peers keep working (R7)

- **Given** an older daemon that does not send `AgentState` and an older controller that does not know the catalog RPC
- **When** they connect to the new controller and new daemon respectively
- **Then** neither fails, and the new capabilities are disabled or reported as unsupported rather than causing a retry loop

### AC8: Verification covers the new paths (R8)

- **Given** the Story's test suite
- **When** it runs without network access
- **Then** signature tampering, canonical bytes, key ids, revision comparison, offline cache, effective-config resolution, `If-Match`, secret-key rejection, and atomic persistence are all covered and pass

### AC9: Catalog signature and revision rules are deterministic (R1)

- **Given** a catalog signed by a pinned key, a copy signed by an unknown key, a copy signed by a revoked key, a copy with the same revision but a different hash, and an expired catalog
- **When** the daemon verifies each
- **Then** only the valid pinned-key catalog replaces the cache; unknown/revoked keys and same-revision/different-hash are rejected; the expired catalog remains readable but cannot authorize new jobs

### AC10: Catalog cache commits as a whole revision (R2)

- **Given** a sync writing a new catalog revision
- **When** the daemon crashes before or after switching the `current` pointer
- **Then** the next start uses either the complete old revision or the complete new revision, never a mixed `catalog.json`/`catalog.sig` pair

## Target Call Chain

1. **Catalog publish.** Controller `main.rs` loads the signed catalog via the new
   `catalog.rs`, validates the signature and schema, and registers it with the
   fleet service.
2. **Catalog fetch.** Daemon `sync.rs` timer or `POST /v1/catalog/sync` →
   `catalog.rs` → `GetAgentCatalog` over the authenticated `Connect`/fleet
   channel → controller `service.rs` → `catalog.rs` → signed bytes.
3. **Catalog verify.** Daemon verifies the Ed25519 signature, SHA-256, revision,
   and schema; on success it atomically writes `catalog.json` and `catalog.sig`;
   on failure it keeps the last-known-good copy.
4. **Local config write.** Desktop app → local socket → `api.rs`
   `PUT /v1/agents/{id}/config` with `If-Match` → `local_config.rs`
   `LocalConfigValidator` → `EffectiveConfig::compute(local, base, local-yaml,
   pushed)` → `Reconciler::apply_with_report` → provider `plan`/write →
   user-level agent files. Startup, reconnect, periodic sync, and controller
   push use the same resolver.
5. **Status.** Daemon `remote.rs` sends `AgentState` and the existing
   `ConfigStatus` over `Connect` → controller `service.rs` → `database.rs`
   (`device_agent_state`, `device_config_status`) → device detail API.

## Open Questions

- Q1: Catalog signing-key rotation: R1 supports multiple pinned keys and an
  overlap window; the operational runbook (publish overlap, revoke old key,
  re-sign cached catalogs) must be documented in `docs/architecture/` before the
  first public release.
- Q2: Whether the controller catalog is file-based or database-backed: Phase 1
  uses a signed file loaded at startup; an upload UI is out of scope.

Local-config validation is resolved in R6: `ProgramsConfig` remains the
structure, but every local write passes `LocalConfigValidator`; arbitrary
pass-through remains controller-managed only.

## Out of Scope

- Downloading, installing, uninstalling, or executing any catalog artifact.
- Desktop app UI for catalog/config management.
- Controller-pushed per-agent configuration.
- Multi-tenant provisioning.
- Auto-update of Agentdesktop itself.
- Windows and Linux installer specifics.
