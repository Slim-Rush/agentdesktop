## Background

Agent jobs now report stable error codes, redacted diagnostics, and a persisted
status. Users need a way to understand a failure and act on it without reading
daemon logs.

This Story adds a chat-based failure assistant. It uses the model access already
configured for the user's installed coding agents — no new Agentdesktop model
configuration and no separate cloud chat service. It is read-only by default;
state-changing actions are allowlisted and require explicit confirmation.
Desktop agent management is STORY-20261026412cfc3ce6a9.

## Requirements

### R1: Chat entry points and context (MUST)

The desktop app MUST open the assistant from a failed job and from an Assistant
view. The context MUST include the job id, agent id/version, job state, stable
error code, redacted error message/diagnostics, catalog revision, and sync
status. The user MUST see what will be sent before the first request.

### R2: Local assistant provider (MUST)

The assistant MUST use a model configuration the user already has for a
discovered coding agent; it MUST NOT introduce a new global model, gateway, or
API-key setting. It MUST invoke only an installed, discovered, allowlisted
provider in a documented non-interactive, read-only mode. Phase 1 providers are
Claude Code and Codex; a provider whose CLI cannot guarantee no tool use MUST
NOT be offered.

Invocation MUST use an executable path from discovery, an argument array (no
shell), a bounded timeout, a bounded stdout/stderr capture, and cancellation.
If no provider is available, the app MUST fall back to rule-based diagnosis.

### R3: Read tools and safe actions (MUST)

The assistant MUST be able to read: job status, recent jobs, diagnostics,
catalog/agent state, and sync status. The only state-changing actions are:
retry install/uninstall, refresh catalog, refresh inventory, and open settings.
Every action MUST be allowlisted, validated against the current job/agent, and
confirmed by the user. The model MUST NOT execute commands, URLs, or actions
directly; the UI renders proposed actions and submits them through the local
daemon API only after confirmation.

### R4: Failure playbooks (MUST)

The assistant MUST map stable error codes to suggested actions:
`checksum_mismatch`/`signature_invalid` → refresh catalog and retry;
`catalog_changed`/`catalog_expired` → refresh catalog;
`unsupported_platform` → explain and disable install;
`permission_denied` → open settings / explain user-scope limits;
`disk_full` → advise freeing space;
`extract_failed`/`install_failed` → retry or collect diagnostics;
`receipt_conflict` → explain modified/unmanaged content;
`timeout` → retry.

### R5: Privacy and redaction (MUST)

The prompt MUST NOT include file contents, environment variables, secret
values, tokens, or full home paths. Diagnostics MUST be redacted before being
sent. Chat history MUST be in memory only unless the user explicitly opts into
persistence. The user MUST be able to clear the conversation.

### R6: Assistant UI (MUST)

The view MUST provide a provider selector, context banner, message list,
loading/streaming state, error and retry, action cards, and a confirmation
modal. It MUST be keyboard accessible and announce new messages/actions with
`aria-live`.

### R7: Audit (MUST)

The app MUST record the provider, job id, action proposed/confirmed, and
outcome. It MUST NOT persist prompt or message content by default.

### R8: Tests (MUST)

Tests MUST cover provider adapter argument construction (no shell), timeout and
output caps, redaction, playbook mapping, action confirmation, and the
rule-based fallback. Tests MUST use a fake CLI and MUST NOT call a real model.

## Technical Design

**UI.** Add an `assistant` view to the desktop shell and a failure-state entry
button. `useAssistant` owns provider discovery, the selected provider, the
message list, context preview, pending action, and cancellation. The existing
`PageBoundary` and shell patterns are reused.

**Provider adapter.** A new `crates/agentdesktop/src/assistant.rs` defines
`ChatProvider` profiles (id, display name, discovery kind, argv template,
timeout, output cap). It uses `std::process::Command` with `args` only, spawns
the discovered executable, kills it on timeout/cancel, captures bounded output,
and redacts before returning. Provider profiles are enabled only after their
non-interactive read-only mode is verified against the tool's documentation; an
unverified profile stays disabled and falls back to rule-based diagnosis.

**No new model config.** The adapter does not read or store API keys; the CLI
uses the agent's existing configuration. The app does not add a gateway URL,
model selector, or secret field.

**Actions.** The playbook derives a closed set of actions from the job error
code; the model may recommend one of those action ids in its response, but the
UI validates it against the allowlist and the current job/agent. Confirmed
actions call the local daemon API. No action carries a shell command or URL.

**Redaction.** The context builder strips home-directory prefixes, token-like
values, environment assignments, and content longer than a fixed limit. It
keeps code, state, agent id/version, and catalog revision.

**Audit.** Append-only local records contain provider, job id, action id,
confirmation, and outcome; no prompt/message content by default.

**Engineering concerns.**

| Concern | Decision |
|---------|----------|
| ui-state-accessibility | Loading/streaming/error/retry, focus management, `aria-live`. |
| api-integration | Local socket reads/actions only; no external network except the provider CLI. |
| security | Executable from discovery, argv array, no shell, timeout/output cap, allowlist actions. |
| write-safety | Confirmation before every state change; retry validated against current job. |
| observability | Audit provider/job/action/outcome; show redacted diagnostics. |
| dependency-supply-chain | No new runtime dependency; provider CLI is already installed by the user. |

### Lateral Scan Results

- **Operation:** show failure diagnostics. **Existing implementation:**
  `StatusView` / job error surfaces. **Assessment:** reuse the data; add a chat
  context builder rather than a second diagnostics source.
- **Operation:** confirm destructive actions. **Existing implementation:**
  `SettingsView`/`DeviceView` confirmation patterns. **Assessment:** reuse the
  modal behavior; no new interaction primitive.
- **Operation:** run a local executable. **Existing implementation:** the
  desktop app already launches `launchctl` on macOS for its daemon. **Assessment:**
  add a constrained provider runner; do not broaden the existing process code.

## Permission Matrix

| Actor | Action | Resource | Decision |
|-------|--------|----------|----------|
| Local user | Open the assistant and read job diagnostics | Local daemon | Allow |
| Local user | Select an installed provider | Discovered coding agents | Allow only for allowlisted profiles |
| Assistant provider | Read job/catalog/sync context | Local daemon | Allow — redacted, read-only |
| Assistant provider | Execute a shell command, URL, or file write | Host | Deny — no such field exists |
| Local user | Retry an install/uninstall after confirmation | Local daemon job API | Allow |
| Local user | Refresh catalog/inventory or open settings | Local daemon / OS | Allow after confirmation |
| Unconfirmed model suggestion | Any state-changing action | Local daemon | Deny |
| Uninstalled or unsupported provider | Answer chat | Assistant | Deny — fall back to rule-based diagnosis |

## Trust Boundaries

- Job diagnostics → redaction (home paths, secrets, env, oversized content) →
  provider prompt. The UI shows the redacted context before sending.
- Provider executable → discovery path + allowlisted argv template → child
  process with timeout/output cap; no shell and no user-supplied arguments.
- Model response → action-id validation against the playbook allowlist → user
  confirmation → local daemon API. Text never becomes a command or URL.
- Chat history → in-memory session only → clear on request; optional persistence
  is explicit opt-in.
- Confirmed action → local socket → daemon job API → audit record.

## Acceptance Criteria

### AC1: Chat opens with redacted job context (R1, R5)

- **Given** a failed job with diagnostics containing a home path and a token-like value
- **When** the user opens the assistant
- **Then** the context preview shows the job/agent/error/catalog fields with those values redacted, and the user can cancel before sending

### AC2: The provider uses the local agent's model configuration (R2)

- **Given** an installed Claude Code or Codex discovery entry
- **When** the user selects it and sends a message
- **Then** the app invokes the discovered executable with an allowlisted argv array and no new gateway/model/API-key setting, and reports no shell execution

### AC3: Unsupported or unavailable providers fall back (R2)

- **Given** no installed provider with a verified read-only profile
- **When** the assistant opens
- **Then** the UI offers rule-based diagnosis and does not spawn an unverified executable

### AC4: Read tools are bounded and redacted (R3, R5)

- **Given** a chat session for a failed job
- **When** the assistant requests job, catalog, or sync context
- **Then** only redacted read data is provided, with bounded size and no file contents, environment variables, or secrets

### AC5: Actions require allowlist and confirmation (R3)

- **Given** a model response proposing `retry_install` and another proposing an unknown action
- **When** the user reviews the action cards
- **Then** the known action is shown with a confirmation step and calls the daemon only after confirmation; the unknown action is ignored

### AC6: Playbooks map stable error codes (R4)

- **Given** each stable error code
- **When** the assistant explains it
- **Then** it offers the mapped suggested action set and no unrelated action

### AC7: UI states and keyboard access are complete (R6)

- **Given** loading, streaming, error, retry, provider-unavailable, and action-confirmation states
- **When** navigated by keyboard
- **Then** focus is managed, new messages/actions are announced via `aria-live`, and the confirmation modal traps and restores focus

### AC8: Audit and tests cover the assistant path (R7, R8)

- **Given** the Story's test suite
- **When** it runs with a fake provider executable
- **Then** argv construction, timeout, output cap, redaction, playbook mapping, confirmation, fallback, and audit records are covered, and no real model is called

## Target Call Chain

1. **Context.** Failed job → `useAssistant` → `get_chat_context` → local daemon
   `GET /v1/jobs/{id}`, `/v1/catalog`, `/v1/sync-status` → redaction →
   context preview.
2. **Provider.** Provider selector → `get_chat_providers` → `/v1/discovery` →
   allowlisted profile → `start_chat` → `assistant.rs` spawns the discovered
   executable with argv only.
3. **Response.** Child stdout/stderr → bounded capture → redaction → message
   list; cancel kills the child.
4. **Action.** Model recommends an action id → UI validates against the
   playbook → confirmation modal → `execute_chat_action` → local daemon job/
   catalog/settings API → audit record.
5. **Fallback.** No verified provider → rule-based playbook rendering, no
   process spawn.

## Out of Scope

- Auto-remediation without confirmation.
- File editing or arbitrary shell execution by the assistant.
- A new global model/gateway/API-key configuration.
- A separate cloud chat service.
- Long-term chat history or cross-device sync.
