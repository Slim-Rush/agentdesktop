## Background

`/project-check` on STORY-20261026c0268fd1f364 found two P1 and several P2
defects in the device lifecycle work. The controller UI cannot submit
retire/revoke because the write handlers require an OIDC bearer token that the
browser does not have. `BeginEnrollment` stores an unbounded
`previous_device_id` in its pending map, so an unauthenticated caller can
amplify memory. Rejected lineage events are attributed to the untrusted
previous device ID and can pollute another subject's device history. The link
decision treats an unknown device state as linkable, concurrent lifecycle
transitions can duplicate audit events, the UI hides audit load-more failures,
and the daemon retries `device_limit_reached` forever without a terminal state.

This Story remediates those findings without changing the fleet protocol,
database ownership model, or dependency set.

## Requirements

### R1: Admin write authorization (MUST)

Admin mutating endpoints (`POST /api/v1/devices/{id}/retire`,
`POST /api/v1/devices/{id}/revoke`, and `POST /api/v1/devices/{id}/jobs`) MUST
use one write-authorization policy:

- when `adminAuth` is configured (OIDC provider plus a non-empty
  `allowedSubjects`), the request MUST carry a valid OIDC bearer token whose
  subject is allowed, exactly as today;
- when `adminAuth` is not configured, a request from the loopback-only admin
  listener MAY be authorized by presenting the header
  `x-agentdesktop-admin: 1`, because that header cannot be set by an HTML form
  and triggers a CORS preflight for cross-origin JavaScript;
- a write without the required credential MUST be rejected with a stable
  `403`/`401` and MUST NOT mutate state.

The actor recorded in audit for the loopback path MUST be
`local#loopback-admin`. Admin GET endpoints MUST continue to use
`require_if_configured`.

### R2: Enrollment input bounds (MUST)

`previousDeviceId` is untrusted. The controller MUST validate it against
`[A-Za-z0-9._-]{1,128}` before storing it in a pending enrollment; an invalid or
oversized value MUST be ignored, not stored. The hostname accepted by
`BeginEnrollment` MUST be non-empty after trimming and at most 255 bytes; a
larger value MUST be rejected before it enters the pending map. The database
enrollment transaction MUST keep its own validation before using the value.
These bounds MUST prevent unauthenticated pending-map memory amplification.

### R3: Rejection audit attribution (MUST)

`device.link_rejected` and `device.limit_rejected` events MUST NOT use the
untrusted previous device ID as `device_id`. They MUST record `device_id = ''`
and keep the attempted previous ID in the payload. A rejection caused by one
subject presenting another subject's previous device ID MUST NOT appear in the
other device's audit history; it MUST remain visible through subject and
global audit filters.

### R4: Fail-closed link decision and stable reasons (MUST)

The controller MUST auto-link only when the previous device exists, has the same
issuer and subject, has the same normalized hostname, and its state is exactly
`active` or `retired`. A `revoked` previous device MUST be rejected with
`device_revoked`; any other non-linkable state MUST be rejected with
`state_unknown`; a previous device that already has `supersededBy` MUST be
rejected with `already_superseded`. The complete stable reason set is
`unknown_device`, `subject_mismatch`, `hostname_mismatch`, `device_revoked`,
`already_superseded`, and `state_unknown`. The new Spec governs this
remediation; the original Story's R3 list is extended by these two reasons.

### R5: Concurrent lifecycle transitions (MUST)

A state transition MUST be applied with a conditional update on the state that
was read (`UPDATE ... WHERE id = $1 AND state = $4`). If the condition does not
match because another request changed the device first, the controller MUST
re-read the state; if it already equals the requested target it MUST return an
idempotent success without a second audit event, otherwise it MUST return a
conflict. At most one `device.retired` or `device.revoked` audit event may be
written for one effective transition.

### R6: Admin UI error handling (MUST)

The controller UI MUST send `x-agentdesktop-admin: 1` on lifecycle POSTs. An
audit-history load-more failure MUST be shown in the audit section and MUST NOT
be stored in the lifecycle-confirmation error slot. Lifecycle success MUST
refresh the device and audit queries and show the resulting state. Confirmation
dialogs MUST keep keyboard focus within the dialog and restore it on close.

### R7: Daemon device-limit terminal state (MUST)

When enrollment fails with gRPC `ResourceExhausted` and the message
`device_limit_reached`, the daemon MUST enter the terminal enrollment state
`deviceLimitReached` instead of retrying with backoff. The desktop snapshot MUST
map that state to `rejected` with an actionable message telling the user to
retire a device or contact an administrator and try again. Logout or the
"Try again" action MUST clear the terminal state and permit a new enrollment
attempt.

### R8: Verification (MUST)

Tests MUST cover: loopback write with and without the header; configured
`adminAuth` still requiring a bearer; enrollment bounds for previous ID and
hostname; rejection attribution across subjects; unknown-state and
already-superseded link rejection; concurrent retire transitions producing one
audit event; the UI audit load-more error state; and the daemon terminal limit
state including logout recovery. The suite MUST NOT require a real OIDC
provider or network.

## Acceptance Criteria

### AC1: Loopback write is authorized only with the CSRF header (R1)

- **Given** a controller with no `adminAuth` and a loopback admin listener
- **When** the UI sends a lifecycle POST with `x-agentdesktop-admin: 1`
- **Then** the transition succeeds, the audit actor is `local#loopback-admin`,
  and the same POST without the header returns `403` without changing state

### AC2: Configured admin auth still wins (R1)

- **Given** `adminAuth` with a non-empty allowlist
- **When** a lifecycle POST omits the bearer token or uses a disallowed subject
- **Then** the request is rejected, and a valid allowed bearer token succeeds

### AC3: Enrollment inputs are bounded (R2)

- **Given** an enrollment begin request with a 4 MiB previous device ID or a
  256-byte hostname
- **When** the controller validates it
- **Then** the oversized previous ID is ignored and not stored, the oversized
  hostname is rejected, and a valid 128-byte previous ID is retained

### AC4: Rejection audit does not pollute another device (R3)

- **Given** subject B presents subject A's device ID
- **When** the link is rejected and the enrollment continues
- **Then** the rejection has an empty device ID and does not appear in device
  A's audit history, while subject B's audit filter still returns it

### AC5: Link decisions are fail-closed (R4)

- **Given** a previous device with state `quarantined` or with
  `supersededBy` already set
- **When** an enrollment presents it
- **Then** the controller writes `state_unknown` or `already_superseded`,
  creates no lineage, and does not retire the previous device

### AC6: Concurrent retires audit once (R5)

- **Given** two concurrent requests to retire the same active device
- **When** both complete
- **Then** one reports `changed: true`, the other reports `changed: false`, and
  exactly one `device.retired` audit event exists

### AC7: UI shows audit load-more failures (R6)

- **Given** an audit page with a next cursor
- **When** the load-more request fails
- **Then** the audit section shows the error and the lifecycle dialog error
  remains empty

### AC8: Daemon stops retrying a device-limit rejection (R7)

- **Given** an enrollment that returns `ResourceExhausted` with
  `device_limit_reached`
- **When** the daemon handles it
- **Then** the enrollment state is `deviceLimitReached`, no further backoff
  attempts occur, the desktop snapshot is `rejected` with the limit message,
  and a logout request returns the daemon to a retryable state

### AC9: The remediation suite is green (R8)

- **Given** the Story's controller, agent, and frontend suites
- **When** they run without real OIDC or network access
- **Then** all new tests and stories pass and the existing lifecycle tests
  remain green

## Target Call Chain

1. **Admin write.** `DeviceView` confirmation → `App.tsx` POST with
   `x-agentdesktop-admin: 1` → `admin::retire_device` / `revoke_device` →
   `AdminAuth::authorize_write` (configured: bearer; loopback: header) →
   `Database::set_device_state` conditional update → audit.
2. **Enrollment bounds.** Daemon `BeginEnrollment` with `previousDeviceId` →
   `FleetAgentService::begin_enrollment` → `OidcProvider::begin` / `begin_device`
   validates hostname and filters an invalid previous ID → bounded
   `PendingEnrollment` → `complete` → `Database::enroll_device_with_policy`.
3. **Rejection audit.** `enroll_device_with_policy` writes `device.link_rejected`
   or `device.limit_rejected` with an empty device ID and the attempted ID in
   the payload.
4. **Link decision.** `enroll_device_with_policy` reads the predecessor and
   accepts only `active`/`retired`, recording one of the six stable reasons
   otherwise.
5. **Daemon limit.** `oidc::enroll` returns a tonic `Status` →
   `remote::enroll_with_retry` classifies `device_limit_reached` →
   `EnrollmentState` = `deviceLimitReached` → `managed_snapshot` → `EnrollmentView`.
6. **UI errors.** `DevicePage` keeps `auditLoadError` separate from
   `transitionError`; `DeviceView` renders both in their own sections.

## Technical Design

### Admin write authorization

Add `AdminAuth::authorize_write(&self, headers) -> Result<AdminActor, (StatusCode, &'static str)>`
and a constant `ADMIN_WRITE_HEADER = "x-agentdesktop-admin"`.

- If `oidc.is_some() && !allowed_subjects.is_empty()`, delegate to the existing
  `authenticate` (bearer + allowlist).
- Otherwise require the header value `1` and return
  `AdminActor { issuer: "local", subject: "loopback-admin" }`.
- Use `authorize_write` in `create_job`, `retire_device`, and `revoke_device`.
- Change the GET `job_status` handler to `require_if_configured` so reads and
  writes use coherent policies.

The admin listener is already restricted to loopback by
`parse_controller`; the custom header is a CSRF defense, not a network
boundary. OWASP recommends a custom request header for AJAX/API CSRF defense
because it triggers a CORS preflight; HTML forms cannot set it. See
<https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html>.

The frontend adds `adminWrite(path, init)` in `api.ts`, which always sets the
header. `App.tsx` uses it for retire/revoke. No token is stored in
`localStorage`; the header is a fixed CSRF marker, not a credential.

### Enrollment bounds

Create `crates/controller/src/device_identity.rs`:

- `MAX_PREVIOUS_DEVICE_ID_BYTES = 128`
- `MAX_HOSTNAME_BYTES = 255`
- `valid_previous_device_id(Option<&str>) -> Option<&str>` enforcing the shape
  and length
- `valid_hostname(&str) -> bool` enforcing trimmed non-empty and the byte cap
- `hostnames_match(&str, &str)` (moved from `database.rs`)

`OidcProvider::begin` and `begin_device` use `valid_hostname` and filter the
previous ID before `insert_pending`. `Database::enroll_device_with_policy`
keeps its existing validation before use. The service passes the request values
through unchanged; invalid values are ignored/rejected at the OIDC boundary,
which is the storage boundary.

### Rejection attribution

`device.link_rejected` and `device.limit_rejected` bind `device_id = ""` and
include `previousDeviceId` in the payload. `device_history` therefore cannot
pull another subject's rejection into a device view. Subject and global audit
filters remain the discovery path for rejected attempts.

### Fail-closed link decision

The decision order becomes:

1. missing previous → `unknown_device`
2. issuer/subject mismatch → `subject_mismatch`
3. normalized hostname mismatch → `hostname_mismatch`
4. state `revoked` → `device_revoked`
5. state not `active`/`retired` → `state_unknown`
6. `supersededBy` present → `already_superseded`
7. otherwise link

Only step 7 retires the predecessor and sets `replacesDeviceId`.

### Conditional lifecycle transition

`set_device_state` keeps the read of the current state, then executes
`UPDATE devices SET state = $2, retired_at = COALESCE(retired_at, $3)
WHERE id = $1 AND state = $4`. If `rows_affected == 0`, re-read the state:

- equal to the target → idempotent success (`changed: false`, no audit)
- otherwise → `InvalidDeviceTransition` conflict

Audit is inserted only when the update affected one row. The transaction keeps
the existing state/audit atomicity.

### Admin UI error handling

`DevicePage` gains `auditLoadError` and passes it to `DeviceView`. The audit
section renders `auditError` for the initial load and `auditLoadError` for
load-more failures. `transitionError` remains scoped to the confirmation
dialog. A new story renders the load-more error state.

### Daemon terminal limit state

`is_device_limit_reached(&anyhow::Error)` walks the error chain for a
`tonic::Status` with `Code::ResourceExhausted` and message
`device_limit_reached`.

In `enroll_with_retry`, on that error:

1. `enrollment.set("deviceLimitReached").await`
2. wait for a logout request; on logout call `complete_unenrolled_logout` and
   continue the retry loop
3. if the logout channel closes, remain pending rather than spinning

`managed_snapshot` maps `"deviceLimitReached"` to `("rejected", Some("This user
has reached the device limit. Retire a device or ask an administrator, then try
again."))`. The existing "Try again" action sends logout, which clears the
terminal state and permits a new attempt.

### Compatibility

- No proto, database, or configuration schema changes are required.
- Existing `adminAuth` deployments keep bearer-only writes.
- Existing daemons that omit `previousDeviceId` are unaffected.
- No new dependency is added.

### Lateral Scan Results

- Admin write authorization: one existing `AdminAuth` implementation in
  `crates/controller/src/admin_auth.rs` and three write call sites in
  `admin.rs`. Extend `AdminAuth`; do not add a second auth store.
- Enrollment validation: one existing validator in `database.rs`. Move the
  shape/length logic into a shared `device_identity` module and reuse it from
  the OIDC and database boundaries.
- Lifecycle transition: one existing `Database::set_device_state`. Extend it
  with a conditional update; do not add a second transition service.
- Admin UI error state: one existing `DevicePage` state owner. Split the audit
  load error from the transition error; do not add a second page container.
- Daemon retry: one existing `enroll_with_retry` loop. Add terminal
  classification there; do not add a second enrollment loop.

### Engineering concerns

| Concern | Decision |
|---|---|
| security | Loopback writes use a CSRF header; configured auth remains bearer-only; rejection events are not attributed to another subject's device. |
| concurrency | Conditional `UPDATE ... WHERE state = $4` plus re-read; one audit per effective transition. |
| input-validation | Previous ID and hostname capped at the OIDC storage boundary; database keeps a second check. |
| observability | Rejections remain visible via subject/global audit; terminal daemon state is visible in the enrollment snapshot. |
| ui-state-accessibility | Separate audit error state; existing native dialog focus behavior retained; no new auth UI. |
| backwards-compatibility | No wire/schema change; configured admin auth behavior unchanged. |

## Trust Boundaries

- Admin listener → loopback only (config validation) → CSRF header or bearer.
- Enrollment request → untrusted previous ID/hostname → bounded pending map →
  validated link decision.
- Audit event → stable subject and reason → admin read APIs; rejection events
  are not attributed to another device.
- Daemon enrollment error → tonic status classification → terminal UI state.

## Open Questions

- Q1: Loopback write mode was selected over an OIDC UI session; a future Story
  may add admin SSO.
- Q2: `already_superseded` and `state_unknown` extend the original R3 reason
  list; this Spec governs the remediation because the original Spec is under
  spec-guard.
- Q3: The CSRF header is a fixed marker, not an authentication secret; it only
  applies when `adminAuth` is unset and the listener is loopback.
- Q4: Admin quota override, hardware attestation, and duplicate-device merging
  remain out of scope.

## Out of Scope

- A full OIDC login/session flow for the controller UI.
- Admin override of `maxDevicesPerUser` or per-team quotas.
- Hardware-backed device attestation.
- Automatic merging of existing duplicate device rows.
- Reactivating a revoked device.
- A live OIDC/mTLS end-to-end test harness.
