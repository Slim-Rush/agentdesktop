## Background

Phase 1 now exposes a signed agent catalog, local configuration authority,
install/uninstall jobs, and job status on the daemon's local socket. The
desktop app still only shows discovery: users cannot see available agents,
install or update them, edit their configuration, or watch job progress without
calling the local API by hand.

This Story adds the Agents view and the Tauri commands it needs. Chat-based
failure diagnosis is STORY-20261026ae47f2938d17; this Story only links to that
entry point.

## Requirements

### R1: Catalog and installed state (MUST)

The desktop app MUST show every agent in the verified catalog with its display
name, platform/architecture support, available versions, and current state:
`notInstalled`, `userInstalled`, `managed`, `updateAvailable`, or
`unsupported`. It MUST combine `/v1/catalog`, `/v1/agents`, and `/v1/discovery`
without treating a discovery-only tool as installable.

### R2: Install, update, and uninstall actions (MUST)

The app MUST start install/update/uninstall through
`POST /v1/agents/{id}/jobs`. Uninstall MUST first request the daemon's dry-run
plan and show the paths to be removed before confirmation. Actions MUST be
disabled when the agent is unsupported, no catalog is available, or another job
is running. The app MUST NOT call a package manager, shell, or any endpoint
outside the local daemon.

### R3: Job progress and history (MUST)

The app MUST show the current job and recent job history with state, progress,
error code, and human-readable error. It MUST poll `/v1/jobs` while a job is
active and stop polling when the view is hidden or the job is terminal. The app
MUST prevent duplicate submissions for the same agent while a job is active.

### R4: Per-agent configuration editor (MUST)

The app MUST read and write one agent's local configuration through
`GET/PUT /v1/agents/{id}/config`, using the returned revision as `If-Match`.
It MUST show validation and 409 conflict errors inline, preserve the editor
contents on failure, and MUST NOT display or persist secret values.

### R5: Catalog and inventory sync status (MUST)

The app MUST show catalog revision, last successful sync, and whether the
catalog is stale. It MUST offer explicit refresh actions for catalog and
inventory and report their outcome.

### R6: UI states and accessibility (MUST)

Every list and action MUST have loading, empty, error, offline, in-progress,
and disabled states. Status MUST NOT rely on color alone. Controls MUST be
keyboard reachable, destructive confirmations MUST trap focus and restore it,
and job updates MUST be announced through an `aria-live` region.

### R7: Safety and privacy (MUST)

All actions go through the local socket API. The UI MUST NOT render raw HTML,
echo secrets, or send agent configuration to any network endpoint. Destructive
actions require explicit confirmation, and the dry-run paths are shown before
an uninstall.

### R8: Tests (MUST)

Storybook/Vitest coverage MUST cover the catalog list states, job progress,
config validation/conflict, uninstall dry-run confirmation, and disabled
actions. Tests MUST use fixtures and MUST NOT install real agents.

## Technical Design

**View and shell.** Add `agents` to the desktop `View` union and a sidebar
entry in `DesktopShell`. The view is a page with a catalog table, a detail
drawer/panel, and a job strip. `useDesktopModel` owns catalog, agents, jobs,
sync status, and the selected agent.

**Tauri commands.** Add thin commands in `crates/agentdesktop/src/main.rs`:
`get_catalog`, `get_agents`, `get_jobs`, `get_job`, `start_agent_job`,
`get_agent_config`, `save_agent_config`, `get_sync_status`,
`refresh_catalog`, and `refresh_inventory`. Each maps to the existing
local-socket API through `agentdesktop-client`; no new HTTP listener.

**Types and client.** Extend `frontend/desktop/src/types.ts` and `backend.ts`
with catalog entries, agent state, job status, sync status, and config
revision. All fields are camelCase to match the local API.

**Interaction.** The catalog table shows state and a primary action. Install and
update are direct actions with a progress row; uninstall opens a dry-run dialog,
lists the receipted paths, and requires a second confirmation. The config
editor is a JSON editor with inline validation; `If-Match` is kept in component
state and refreshed after a successful save or a 409.

**Polling.** Poll `/v1/jobs` every 1s while a job is active, every 5s otherwise,
and stop when `document.hidden`. A generation counter prevents an older poll
from replacing a newer result. The existing shell refresh remains independent.

**Design system.** Reuse `@agentdesktop/ui` primitives, existing CSS tokens, and
the desktop shell layout. No new design system or marketing styling. Tables
follow `DeviceTable`/`ToolInventory` patterns; status chips combine icon, text,
and color.

**Engineering concerns.**

| Concern | Decision |
|---------|----------|
| ui-state-accessibility | Every async surface has loading/empty/error/disabled; focus trap and `aria-live`. |
| api-integration | Only local socket commands; bounded polling; no external calls. |
| write-safety | Uninstall dry-run + confirmation; config `If-Match`; preserve editor on failure. |
| observability | Show job error code, detail, revision, and sync timestamps. |
| security | No raw HTML, no secrets, no shell/package-manager calls. |

### Lateral Scan Results

- **Operation:** display discovered tools. **Existing implementation:**
  `ToolsView` + `ToolInventory`. **Assessment:** reuse the inventory component;
  add a separate catalog/action layer rather than overloading discovery.
- **Operation:** mutate managed state. **Existing implementation:**
  `SettingsView` program choice and `DeviceView` delete. **Assessment:** reuse
  the confirmation-dialog pattern; add job actions through the daemon.
- **Operation:** poll local state. **Existing implementation:**
  `useDesktopModel` status polling. **Assessment:** extend with job polling;
  do not add a second global poll loop.

| Local user | Write config for an unknown agent | Local daemon config API | Deny |

| Remote network caller | Reach the local API | Local daemon | Deny — socket/pipe only |

## Trust Boundaries

- Catalog and agent state → local socket → React state. The UI renders only
  escaped text; no raw HTML.
- Config editor input → 256 KiB/depth/schema validation in the daemon → atomic
  local config write. The UI displays key names, not secret values.
- Action buttons → local job API with catalog id/version → daemon verification.
  The UI cannot supply a shell command or arbitrary URL.
- Job polling → local socket → status chips and `aria-live`; stale responses
  are discarded by a generation counter.

## Acceptance Criteria

### AC1: Catalog and installed state are visible (R1)

- **Given** a catalog with `claude-code` and a discovery entry for the same agent
- **When** the Agents view loads
- **Then** the row shows supported platform/version, `managed` state, and the available versions; a discovery-only tool appears as unsupported and has no install action

### AC2: Install, update, and uninstall use the daemon job API (R2)

- **Given** a cataloged agent with an available version
- **When** the user selects Install
- **Then** the app posts to `/v1/agents/{id}/jobs`, shows a running job, and does not call any package manager or external endpoint

### AC3: Uninstall shows the dry-run paths first (R2, R7)

- **Given** a managed agent
- **When** the user selects Uninstall
- **Then** the app requests a dry-run, lists the receipted paths, and only submits the uninstall after explicit confirmation

### AC4: Job progress and history are accurate (R3)

- **Given** an active job and a hidden window
- **When** the job changes state or the window becomes visible
- **Then** polling stops while hidden, resumes when visible, and the latest state/error is shown exactly once without duplicate submission

### AC5: Configuration edits respect revisions and validation (R4)

- **Given** an agent config at revision 3
- **When** the user saves with an outdated revision or a secret-bearing key
- **Then** the editor keeps its contents, shows the 409/validation error inline, and does not display the secret value

### AC6: Sync status and refresh are visible (R5)

- **Given** a stale catalog
- **When** the user opens the sync status and selects Refresh catalog
- **Then** the UI shows the last successful sync and reports the refresh result

### AC7: States and accessibility are complete (R6)

- **Given** loading, empty, error, offline, in-progress, and disabled states
- **When** each is rendered and navigated by keyboard
- **Then** every state has text (not color alone), focus is trapped/restored in confirmations, and job updates are announced through `aria-live`

### AC8: Tests cover the UI surface without real installs (R8)

- **Given** the Story's Storybook/Vitest suite
- **When** it runs with fixtures
- **Then** catalog states, job progress, config conflict, dry-run confirmation, and disabled actions are covered and no real agent is installed

## Target Call Chain

1. **Load.** `useDesktopModel` → `get_catalog` / `get_agents` / `get_sync_status`
   → Tauri command → `agentdesktop-client` → daemon `GET /v1/catalog`,
   `/v1/agents`, `/v1/sync-status`.
2. **Install/update.** Agent row action → `start_agent_job` → Tauri command →
   daemon `POST /v1/agents/{id}/jobs` → `JobExecutor` → `Installer`.
3. **Uninstall.** Action → dry-run job request (`dryRun: true`) → daemon returns
   paths → confirmation dialog → real job request.
4. **Progress.** `useDesktopModel` job poll → `get_jobs` → daemon
   `GET /v1/jobs` → status chips + `aria-live`.
5. **Config.** Editor load → `get_agent_config`; save → `save_agent_config`
   with `If-Match` → daemon `PUT /v1/agents/{id}/config` → `LocalConfigStore`.
