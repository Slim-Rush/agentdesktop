## Background

The controller assigns a random UUID v4 at enrollment and authenticates the device
with a locally generated key pair plus a controller-issued X.509 client certificate.
A reinstall, ad-hoc code-signature change, or lost Keychain item makes the old private
key unusable; the daemon re-enrolls and the controller inserts a new device row. Job,
usage, telemetry, and audit history then split across device IDs. There is also no
per-user device limit: only the global pending-enrollment cap applies. The audit table
is write-only, and deleting a device cascades job and telemetry rows.

This Story makes device identity continuity, per-user device limits, and device
audit a product feature instead of leaving them as incidental behavior.

## Requirements

### R1: Device lifecycle and soft deletion (MUST)

`devices` MUST have a lifecycle state of `active`, `retired`, or `revoked`; existing
rows migrate to `active`. An admin MUST be able to retire or revoke a device.
Retired and revoked devices MUST be denied fleet authentication. The normal admin
flow MUST NOT physically delete a device, and retirement/revocation MUST NOT delete
its job, usage, telemetry, discovery, or audit records. Each transition MUST be
idempotent and audited.

### R2: Per-user device limit (MUST)

The controller configuration MUST provide
`devicePolicy.maxDevicesPerUser`, a positive integer defaulting to 5. At completion
of a non-replacement enrollment the controller MUST count `active` devices for the
enrolling OIDC `issuer + subject`. At or above the limit it MUST reject the
enrollment with a stable `device_limit_reached` error, MUST NOT create a device row,
and MUST write a `device.limit_rejected` audit event. Retired and revoked devices
MUST NOT count. A valid linked re-enrollment MUST replace the old active device
without increasing the active count. The count-and-create operation MUST be
serialized per subject so concurrent enrollments cannot exceed the limit.

### R3: Re-enrollment lineage (MUST)

The daemon MUST send `previousDeviceId` from the local identity metadata when it
re-enrolls after losing the usable private key. The controller MUST auto-link the
new enrollment only when all of the following hold:

- the previous device exists;
- its `enrolledByIssuer` and `enrolledBySubject` equal the new OIDC principal;
- its hostname equals the new hostname after trimming and ASCII case-folding;
- its state is `active` or `retired`, never `revoked`.

On a valid link the old device becomes `retired`, receives `supersededBy = new id`
and `retiredAt`; the new device receives `replacesDeviceId = old id`; the active
count is unchanged by the replacement. The event MUST be audited as
`device.re_enrolled`. If any condition fails, the enrollment MUST continue as a new
device subject to R2, and the controller MUST write `device.link_rejected` with a
stable reason (`unknown_device`, `subject_mismatch`, `hostname_mismatch`, or
`device_revoked`). Hostname alone MUST NOT establish lineage. A `revoked` device
MUST never be reactivated by auto-linking.

### R4: Audit read model and device history (MUST)

`audit_events` MUST gain a `subject` column and indexes for subject/action time
queries. The controller MUST record at least `device.enrolled`,
`device.re_enrolled`, `device.link_rejected`, `device.limit_rejected`,
`device.retired`, and `device.revoked`. Audit payloads MUST NOT contain secrets,
tokens, certificate private material, or diagnostic file contents.

The admin API MUST expose:

- `GET /api/v1/devices/{id}/audit` with cursor pagination;
- `GET /api/v1/audit` filterable by subject, action, device, and time range;
- device detail fields for state, retired time, replacement/superseded IDs, and the
  current active-device count for the subject.

Device history MUST follow the `replacesDeviceId`/`supersededBy` chain, bounded to
32 devices, so a current device's audit view includes its predecessors. Audit rows
MUST remain readable after retirement and MUST NOT be deleted by the admin UI.

### R5: Admin lifecycle UI (MUST)

The controller device list MUST show lifecycle state and allow filtering. The device
detail MUST show lifecycle metadata, lineage, active-device count, and audit history.
Retire and revoke MUST require an explicit confirmation and MUST show the resulting
state. The old hard-delete action MUST be removed from the normal UI. Settings MUST
show `maxDevicesPerUser`. The UI MUST remain keyboard accessible and announce async
state changes.

### R6: Migration and compatibility (MUST)

A migration MUST add the lifecycle columns, lineage columns, audit subject column,
and indexes without losing existing data. Existing devices and audit rows MUST
remain readable; existing devices become `active` with no lineage. The enrollment
proto change MUST be additive. Older daemons that do not send `previousDeviceId`
MUST still enroll as new devices subject to R2. The controller MUST be upgraded
before daemons. Automatic backfill or merging of existing duplicate devices is out
of scope.

### R7: Automated tests (MUST)

Tests MUST cover: the fifth and sixth active device (allow/reject), a replacement at
the limit not increasing the count, retired/revoked devices not counted, successful
auto-link, hostname mismatch, subject mismatch, revoked previous device, audit
read/pagination/lineage, soft retirement preserving job and usage rows, retired and
revoked device authentication denial, migration from the pre-change schema, and a
concurrent enrollment attempt that cannot exceed the limit.

## Acceptance Criteria

### AC1: Retire and revoke preserve history (R1)

- **Given** an active device with job, usage, telemetry, discovery, and audit rows
- **When** an admin retires it, then revokes it
- **Then** the device is denied fleet authentication, its state and timestamps are
  visible, no child rows are deleted, and both transitions have audit events

### AC2: Per-user limit is enforced (R2)

- **Given** a controller with `maxDevicesPerUser: 5` and four active devices for a user
- **When** the user enrolls a fifth and then a sixth unrelated device
- **Then** the fifth succeeds, the sixth fails with `device_limit_reached`, no sixth
  device row exists, and a `device.limit_rejected` audit event is written

### AC3: A valid re-enrollment replaces the old device (R3)

- **Given** an active device and a new daemon enrollment carrying its previous device
  ID, same OIDC subject, and same hostname
- **When** the new enrollment completes
- **Then** the old device is retired, the new device references it, the active count
  is unchanged, and the event is audited as `device.re_enrolled`

### AC4: Invalid lineage does not merge devices (R3)

- **Given** a previous device with a different subject, different hostname, or
  `revoked` state
- **When** a new enrollment presents that previous device ID
- **Then** no lineage is written, the old device is unchanged, a
  `device.link_rejected` audit event records the reason, and the new enrollment is
  subject to the normal active-device limit

### AC5: Audit history follows the device chain (R4)

- **Given** a device with two predecessors linked through `replacesDeviceId` and
  `supersededBy`
- **When** an admin reads the current device's history
- **Then** audit events from the current device and both predecessors are returned
  in time order with pagination, and no secret-bearing payload is exposed

### AC6: Admin UI exposes lifecycle and history (R5)

- **Given** a retired device with a predecessor
- **When** an admin opens the device list and detail
- **Then** the state badge, lineage, active-device count, and audit history are
  visible; retire/revoke require confirmation; the hard-delete action is absent

### AC7: Migration preserves existing data (R6)

- **Given** a database created before this Story with devices and audit rows
- **When** the controller migration runs
- **Then** every existing device is `active`, every existing audit row survives with
  its original device ID, and the new indexes exist

### AC8: Tests cover the identity path (R7)

- **Given** the Story's test suite on SQLite and the controller integration surface
- **When** it runs
- **Then** limit, replacement, link rejection, audit lineage, soft retirement, auth
  denial, migration, and concurrency are covered without real OIDC or network access

## Target Call Chain

1. **Enrollment.** Daemon `oidc::enroll` reads the previous device ID from
   `identity.json`, calls `BeginEnrollment` with it, completes OIDC, then calls
   `CompleteEnrollment` with the CSR and previous ID.
2. **Controller.** `FleetAgentService::complete_enrollment` resolves the OIDC
   principal, then `Database::enroll_device_with_policy` opens a per-subject
   transaction, resolves lineage, counts active devices, inserts the device, retires
   the predecessor when linked, writes audit rows, and returns the certificate.
3. **Authentication.** `authenticate_device_certificate_identity` loads the device
   state and rejects `retired`/`revoked`; `Hello` cannot override the certificate
   device ID.
4. **Audit.** `admin::device_audit` and `admin::audit_events` query `audit_events`
   with parameterized filters; `Database::device_history` walks the lineage chain.
5. **UI.** `App.tsx` → `/devices` / `/devices/{id}` → DeviceTable/DeviceView →
   lifecycle badges, lineage, audit history, retire/revoke confirmation.

## Technical Design

### Data model

Add to `devices`:

- `state TEXT NOT NULL DEFAULT 'active'`
- `retired_at BIGINT NULL`
- `superseded_by TEXT NULL`
- `replaces_device_id TEXT NULL`
- index `(enrolled_by_issuer, enrolled_by_subject, state)` and `(superseded_by)`

Add to `audit_events`:

- `subject TEXT NOT NULL DEFAULT ''`
- index `(subject, created_at)` and `(action, created_at)`
- backfill `subject` from the referenced device's `enrolled_by_subject` when the
  device still exists; leave empty otherwise

`maxDevicesPerUser` lives in `ControllerConfig`:

```yaml
devicePolicy:
  maxDevicesPerUser: 5
```

Validation: must be greater than 0 and at most 1000. Default 5.

### Enrollment transaction

`Database::complete_enrollment` is the single owner of the count/link/insert
operation. It opens a transaction and obtains a per-subject lock:

- SQLite: `BEGIN IMMEDIATE` (the write lock serializes enrollment).
- PostgreSQL: `pg_advisory_xact_lock(hashtext(issuer || ':' || subject))`.

Inside the transaction:

1. Validate `previousDeviceId` shape (`[A-Za-z0-9._-]`, <= 128) or ignore it.
2. Load the previous device if supplied; evaluate R3.
3. If linked, update the previous row to `retired`, `retired_at = now`,
   `superseded_by = new_id`.
4. If not linked, count `active` devices for the subject; reject with
   `device_limit_reached` when `count >= maxDevicesPerUser`.
5. Insert the new device with state `active`, `replaces_device_id` when linked.
6. Insert audit rows; commit.
7. Only after commit issue the certificate (or issue inside the transaction after
   validation and before commit; the row is the source of truth).

If certificate issuance fails, the transaction MUST not commit a device row. The
implementation MUST return a stable error code and leave the previous device
untouched.

### Auto-link rules

The previous device ID is untrusted input. The controller MUST compare it against
the database and the authenticated OIDC principal. Hostname comparison uses
`trim().to_ascii_lowercase()`. The controller MUST NOT link when the previous device
is `revoked`, belongs to another subject, has a different hostname, or has been
replaced by a different device. Linking a `retired` predecessor is allowed to
preserve multi-hop history. The audit payload carries old/new IDs and the link
decision, never the certificate or token.

### Authentication state

`DevicePrincipal` gains the lifecycle state. Every authenticated fleet call and
stream revalidation checks `active`; retired/revoked returns `permission_denied`
with a stable `device_retired` or `device_revoked` status. The device cannot clear
the state by presenting a valid certificate; only an admin can change it. Revoked
devices are never auto-linked back to active.

### Audit API

`GET /api/v1/audit` accepts `subject`, `action`, `deviceId`, `before`, `limit`
(1-200, default 50). `GET /api/v1/devices/{id}/audit` accepts `before` and `limit`
and expands the device lineage (current + predecessors, max 32), returning
`{events, nextCursor}`. Admin reads use `require_if_configured`; admin writes use
the existing explicit `authenticate` path. Audit rows are append-only; no endpoint
updates or deletes them.

`GET /api/v1/devices/{id}` adds `state`, `retired_at`, `superseded_by`,
`replaces_device_id`, and `active_devices_for_subject`. The devices list adds
`state` and supports a state filter.

### Admin UI

- Devices list: state badge, filter, no hard-delete action.
- Device detail: lifecycle card, lineage chain, audit history, retire/revoke
  confirmations, active count.
- Settings: show `maxDevicesPerUser`.
- Use existing controller table/card/button components; no new dependency.

### Migration and compatibility

Add a single migration after `0007_audit_events.sql`. Existing devices default to
`active`; lineage columns are null. Proto adds `previous_device_id = 4` to
`BeginEnrollmentRequest` only (additive). Older daemons omit it and enroll as new.
Older controllers ignore it; upgrade controller first. Existing duplicate devices
are not merged automatically; admins can retire them, with audit retained.

### Lateral Scan Results

- Enrollment creation: one current implementation in
  `crates/controller/src/service.rs` (`enroll_device`) and
  `crates/controller/src/database.rs` (`enroll_device`) — extend the existing path,
  do not add a second enrollment service.
- Device lookup/authentication: one existing path in `service.rs`
  (`authenticate_device_certificate_identity`) — reuse it and add state checks.
- Audit writes: one existing `insert_audit` helper — reuse it; add read queries
  instead of a second audit store.
- Device deletion: one admin handler and one DB method — replace the normal flow
  with lifecycle transitions.
- UI device detail: existing `DeviceView`/`DeviceTable` — extend.

## Permission Matrix

| Actor | Action | Resource | Decision |
|---|---|---|---|
| Local user | Enroll this device with OIDC | Controller enrollment | Allow |
| Local user | Auto-link to their own previous device | Device lineage | Allow only with same subject + hostname + non-revoked predecessor |
| Local user | Link to another subject's device | Device lineage | Deny |
| Admin | Read devices, lineage, audit | Admin API | Allow after configured auth |
| Admin | Retire/revoke a device | Device lifecycle | Allow after configured auth; audited |
| Retired/revoked device | Fleet API or stream | Controller | Deny |
| Admin | Hard-delete a device in normal UI | Device | Deny — use retire/revoke |

## Trust Boundaries

- OIDC access token → principal (`issuer`, `subject`, groups) → enrollment identity.
- Previous device ID → database lookup → subject/hostname/state checks → lineage.
- Device certificate → mTLS peer identity → state check → fleet API.
- Audit payload → stable IDs and reason codes → admin read API; no token, key, or
  diagnostic content.
- Device count/link decision → per-subject transaction → device row + audit.

## Open Questions

- Q1: Default limit is 5 (confirmed); `0`/unlimited is not supported in this Story.
- Q2: Auto-link requires previous ID + same subject + same hostname; hostname-only
  linking is deliberately rejected.
- Q3: Retired/revoked devices are denied; reactivation is an admin follow-up.
- Q4: Admin override of the per-user limit and hardware attestation are follow-ups.
- Q5: LLM model entitlement/seat policy is a separate Story.

## Out of Scope

- Per-user LLM model/seat authorization and gateway policy.
- Hardware-backed device attestation or a hardware fingerprint.
- Automatic merging/backfilling of existing duplicate device rows.
- Admin quota override, long-term audit export, and external SIEM integration.
- Reactivating a retired or revoked device.
